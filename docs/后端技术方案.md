## 1. 后端职责边界

| 职责 | 说明 |
| --- | --- |
| 路网数据服务 | 提供路口、进口道、路段信息 |
| 配时优化引擎 | Webster 模型计算周期与绿信比，输出四相位方案 |
| 交通流仿真 | 按时间生成各进口道流量、排队、延误（实测未覆盖时的兜底） |
| 实测接入 | 拉取百度路段级实时路况，反推为进口道饱和度与排队 |
| 指标评价 | 计算优化前后延误/排队/通行量/停车次数及改善率 |
| 事件服务 | 交通事件增删查 |
| 数据落库 | 历史流量与配时方案留痕，支持回溯对比 |

**不做**：真实信号机对接（公安交管封闭系统，个人无法接入）、用户体系（本期无登录）。
**已做**：路段级实时路况抓取（百度交通态势，反推到进口道；不等于进口道直接观测）。

## 2. 数据源定位（2026-11-04 修订：已接入百度实测）

后端采用 **`HybridDataSource`：实测优先、缺测回落仿真**。

```
┌──────────────────────────────────────────────┐
│  Service 层（只依赖 IDataSource 接口）          │
├──────────────────────────────────────────────┤
│  HybridDataSource                            │
│    ├─ BaiduTrafficService ← 实测（异步快照）   │
│    └─ SimulationDataSource ← 仿真（同步兜底）  │
└──────────────────────────────────────────────┘
```

### 2.1 各数据源能拿什么、不能拿什么（实测核查）

| 数据源 | 能提供 | 不能提供 | 在本项目的角色 |
| --- | --- | --- | --- |
| **百度地图 · 交通态势** `GET /traffic/v1/road` | 路段级 `congestion_sections`：`status`（畅通/缓行/拥堵/严重）、`speed`、`congestion_distance`、`congestion_trend`、`section_desc`（含方位，如"东向西"） | **进口道分方向流量**、饱和流率、信号配时参数 | 进口道饱和度与排队的**反推来源**（个人 AK 实测可用，20 条道路串行查询） |
| **仿真引擎**（自建） | 进口道分方向流量 `q`、饱和流率 `s`、排队、延误 | —— | 实测未覆盖部分的兜底；保证任何情况下都有数据 |
| **OSM** | 真实路网拓扑、信号灯点位、WGS84 坐标 | 流量、配时 | P3：替换手工示意坐标 |
| **花瓣 Petal Maps** | 底图 SDK、POI、地理编码 | 实时路况 | 端侧真实底图（可选增强） |

### 2.2 硬结论（修订）

> **地图 API 不能直接作为配时输入，但能作为"实测约束"。**
> Webster 需要的是进口道分方向流量与饱和流率，百度同样不提供；
> 但它提供的路段拥堵区段（车速、拥堵距离、方向、趋势）足以**反推**出进口道的饱和度与排队。
> 因此本项目采用「实测反推 + 仿真兜底」，并在每条进口道上用 `source`（`BAIDU` / `SIM`）与 `note` 明细如实标注来源。

反推链条（`algo/reverse.ts` + `algo/measured.ts`）：

| 实测字段 | 换算 | 产物 |
| --- | --- | --- |
| `speed` | BPR 反函数 → 状态区间约束 → 趋势微调 | 饱和度 |
| `congestion_distance` | × 长度占比 ÷ 车头间距 | 排队车辆数 |
| `section_desc` 方位 | 方位 → 进口道（东向西 → EAST 进口…） | 只覆盖对应进口道，反向不受影响 |
| `congestion_sections` 为空 | 判定畅通 | 只约束饱和度上限（0.2~0.55），保留各路口/时段差异 |

### 2.3 落地方式

| 层 | 文件 | 状态 |
| --- | --- | --- |
| 百度实测 | `service/BaiduTrafficService.ts`（60 s 缓存、串行查询、限流 2 s 重试、失败只记 `failedRoads`） | ✅ |
| 定时刷新 | `task/realtimeTask.ts`（启动预热 + 每 45 s 刷新内存快照；未配 AK 时跳过） | ✅ |
| 反推 | `algo/reverse.ts`（BPR 反解 / 区间约束 / 趋势 / 区段-路段匹配）、`algo/measured.ts`（单段反推与畅通约束） | ✅ |
| 混合装配 | `source/HybridDataSource.ts`（按快照覆盖进口道，`name` 透出 `BAIDU+SIM` / `SIMULATION`） | ✅ |
| 仿真兜底 | `source/SimulationDataSource.ts` | ✅ |
| 真实路网坐标 | `data/network.ts`（当前为公开底图目视核对的近似值） | ❌ P3 |

> **配置**：AK 放在 `server/.env` 的 `BAIDU_AK=...`（`config.ts` 零依赖读取，`.env` 不进 Git）。
> 未配置时 `BaiduTrafficService` 直接返回 `ok=false`，接口行为不变，只是退化为纯仿真。

## 5. 数据模型与存储

### 5.1 实体（与端侧 `entry/src/main/ets/model/` 同名同字段）

```ts
// src/types/Intersection.ts —— 与端侧保持一致，禁止另起命名
export type ApproachDir = 'EAST' | 'WEST' | 'SOUTH' | 'NORTH';
export type IntersectionType = 'CROSS' | 'T_SHAPE' | 'RING';

export interface Approach { dir: ApproachDir; lanes: number; saturationFlow: number; }
export interface Intersection {
  id: string;            // INT_01 ~ INT_15
  name: string;
  longitude: number;
  latitude: number;
  type: IntersectionType;
  approaches: Approach[];
}
export interface RoadSegment { id: string; name: string; fromId: string; toId: string; lanes: number; }
```

**命名约定（重要）**：端侧用 `intersectionId`、路段用 `fromId/toId`、时间为毫秒时间戳。
接口层一律输出**驼峰 + 毫秒时间戳**，数据库内部可用下划线列名，映射只在 `store/` 层做一次，避免两套命名污染上层。

### 5.2 存储设计（P2 起，SQLite）

| 表 | 说明 | 对应端侧 |
| --- | --- | --- |
| `intersection` | 路口 | `Intersection` |
| `approach` | 进口道 | `Approach` |
| `road_segment` | 路段 | `RoadSegment` |
| `signal_plan` | 配时方案 | `SignalPlan` |
| `signal_phase` | 相位明细 | `SignalPhase` |
| `flow_record` | 5 分钟粒度流量 | `FlowRecord` |
| `evaluation` | 优化评价 | `Evaluation` |
| `traffic_event` | 事件 | `TrafficEvent` |

> **✅ 已落地（2026-11-03）**：上表 8 张中只落地**事件表**，实际表名 `event`（列与下方 `traffic_event` 等价），
> 代码见 `server/src/store/sqlite.ts`，使用 Node 内置 `node:sqlite`，零第三方依赖。
> 其余 7 张为回溯/历史用途，当前未建——交通状态量是确定性仿真的实时派生量，落库不产生新信息（见设计文档 §8.3）。
> 实测：写入一条 → 重启服务 → 数据仍在；多台设备访问同一后端即共享同一份事件。

```sql
-- data/schema.sql（SQLite）
CREATE TABLE IF NOT EXISTS intersection (
  id           TEXT PRIMARY KEY,              -- INT_01
  name         TEXT NOT NULL,
  longitude    REAL NOT NULL,
  latitude     REAL NOT NULL,
  type         TEXT NOT NULL DEFAULT 'CROSS',
  source       TEXT NOT NULL DEFAULT 'OSM'    -- 路网来源：OSM / MANUAL
);

CREATE TABLE IF NOT EXISTS approach (
  intersection_id TEXT NOT NULL,
  dir             TEXT NOT NULL,              -- EAST/WEST/SOUTH/NORTH
  lanes           INTEGER NOT NULL DEFAULT 2,
  saturation_flow INTEGER NOT NULL DEFAULT 1650,
  PRIMARY KEY (intersection_id, dir)
);

CREATE TABLE IF NOT EXISTS road_segment (
  id      TEXT PRIMARY KEY,
  name    TEXT NOT NULL,
  from_id TEXT NOT NULL,
  to_id   TEXT NOT NULL,
  lanes   INTEGER NOT NULL DEFAULT 2
);

CREATE TABLE IF NOT EXISTS signal_plan (
  id                  INTEGER PRIMARY KEY AUTOINCREMENT,
  intersection_id     TEXT NOT NULL,
  plan_name           TEXT NOT NULL,
  cycle_length        INTEGER NOT NULL,
  lost_time           INTEGER NOT NULL DEFAULT 16,
  optimized           INTEGER NOT NULL DEFAULT 1,
  before_cycle_length INTEGER NOT NULL DEFAULT 120,
  create_time         INTEGER NOT NULL        -- 毫秒时间戳
);
CREATE INDEX IF NOT EXISTS idx_plan_int_time ON signal_plan(intersection_id, create_time);

CREATE TABLE IF NOT EXISTS signal_phase (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  plan_id    INTEGER NOT NULL,
  phase_id   INTEGER NOT NULL,
  name       TEXT NOT NULL,
  green      INTEGER NOT NULL,
  yellow     INTEGER NOT NULL DEFAULT 3,
  all_red    INTEGER NOT NULL DEFAULT 1,
  movements  TEXT NOT NULL DEFAULT ''         -- 逗号分隔：EAST,WEST
);

CREATE TABLE IF NOT EXISTS flow_record (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  intersection_id  TEXT NOT NULL,
  dir              TEXT NOT NULL,
  volume           INTEGER NOT NULL,          -- 辆/h
  queue_length     INTEGER NOT NULL DEFAULT 0,
  delay            REAL NOT NULL DEFAULT 0,   -- s/辆
  saturation       REAL NOT NULL DEFAULT 0,   -- v/c
  record_time      INTEGER NOT NULL           -- 毫秒时间戳
);
CREATE INDEX IF NOT EXISTS idx_flow_int_time ON flow_record(intersection_id, record_time);

CREATE TABLE IF NOT EXISTS evaluation (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  intersection_id  TEXT NOT NULL,
  scenario         TEXT NOT NULL,             -- 早高峰 / 平峰 / 晚高峰
  before_delay REAL, after_delay REAL,
  before_queue REAL, after_queue REAL,
  before_throughput INTEGER, after_throughput INTEGER,
  before_stops REAL, after_stops REAL,
  create_time INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS traffic_event (
  id          TEXT PRIMARY KEY,
  type        INTEGER NOT NULL,               -- 0事故 1施工 2管制 3拥堵 4其他
  title       TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  road_name   TEXT NOT NULL DEFAULT '',
  longitude   REAL, latitude REAL,
  impact      INTEGER NOT NULL DEFAULT 1,     -- 1轻微 2一般 3严重
  create_time INTEGER NOT NULL
);
```

**E-R 关系**

```
intersection 1─n approach
intersection 1─n signal_plan 1─n signal_phase
intersection 1─n flow_record
intersection 1─n evaluation
road_segment n─1 intersection (from_id / to_id)
```

> 若后续改用 MySQL：类型映射 `TEXT→VARCHAR`、`INTEGER→INT/BIGINT`、`REAL→DOUBLE`、毫秒时间戳 `INTEGER→BIGINT`（或 `DATETIME`），其余结构不变。

## 6. 接口契约（P0 定稿，✅ 12 个接口已全部实现）

统一前缀 `/api/v1`；统一响应 `{ "code": 0, "message": "success", "data": {}, "timestamp": 0 }`；
**字段一律驼峰，与端侧模型同名**；时间统一毫秒时间戳。

### 6.1 实时通道（如实说明：HTTP 轮询，未用 WebSocket）

**当前端侧与后端之间是 HTTP 短轮询，全站统一 30 s**：

| 端侧位置 | 请求 | 间隔 | 常量 |
| --- | --- | --- | --- |
| 首页 / 路况 / 路口详情 / 配时 / 事件 / 收藏 | `/traffic/index`、`/traffic/flow`、`/traffic/flow/{id}`、`/events` 等 | 30 s | `AppConstants.REFRESH_DATA_MS`（`RefreshController` 统一） |
| 手动刷新（按钮、下拉） | 同上 | 点击触发 | 与定时共用 `trigger()`，刷新中防重入 |

后端 `package.json` 只有 `fastify` 一个运行时依赖，**无 `ws` / `socket.io`**，`index.ts` 未注册任何升级端点；端侧同样无 WebSocket 客户端代码。

后端另有 **45 s 定时任务**（`task/realtimeTask.ts`）刷新百度路况到内存快照（百度侧 60 s 缓存），
业务接口同步读取最新快照，因此接口响应时间不受百度 RT 影响。

**暂不引入 WebSocket 的理由**：20 路口规模下请求量极小，30 s 延迟对态势展示完全可接受；长连接在鸿蒙端需自行实现心跳、
断线重连与降级，反而增加演示期的不确定性。

**可选升级路径（P2，未做）**：新增 `/ws` 端点，`flowTask` 生成流量后广播 `{ type: 'flow', data: [...] }`；
端侧建 `WebSocketClient`（30 s 心跳 + 指数退避重连），**并保留轮询作为降级通道**。

| 方法 | 路径 | 说明 | 响应 `data` |
| --- | --- | --- | --- |
| GET | `/health` | **健康检查 / 数据源探测**（端侧三态降级依赖） | `{ status: 'ok', dataSource: 'BAIDU+SIM' \| 'SIMULATION', algoVersion, serverTime }` |
| GET | `/area/intersections` | 路口列表（含进口道） | `{ intersections: Intersection[] }` |
| GET | `/area/segments` | 路段列表 | `{ segments: RoadSegment[] }` |
| GET | `/traffic/index` | 片区拥堵指数（均速优先取实测加权） | `{ areaName, index, avgSpeed, updateTime }` |
| GET | `/traffic/flow` | 全部路口实时流量（可带 `codes=INT_01,INT_02`） | `{ flows: FlowRecord[] }`，每条进口道含 `source` / `note` |
| GET | `/traffic/flow/{id}` | 单路口流量 | `FlowRecord` |
| GET | `/signal/plan/{id}` | 当前配时方案（输入为实测反推的饱和度） | `SignalPlan` |
| POST | `/signal/optimize/{id}` | 触发优化（body 可选 `{ scenario }`） | `{ plan: SignalPlan, evaluation: Evaluation }` |

## 7. 核心算法实现（★ 平移自端侧，口径必须一致）

> 以下 TS 代码与 `entry/src/main/ets/mock/XianWallMock.ets` 逐条对应。

### 7.1 Webster 最优周期

```ts
// src/algo/webster.ts
const MIN_CYCLE = 60, MAX_CYCLE = 150;
const MIN_GREEN_THROUGH = 10, MIN_GREEN_LEFT = 8;

export interface PlanResult { cycle: number; greens: number[]; lostTime: number; }

/**
 * @param yEW 东西直行流量比  @param yNS 南北直行流量比
 * 左转相位按直行的 30% 折算（仿真未拆分转向流量）
 */
export function calculate(yEW: number, yNS: number, lostTime: number = 16): PlanResult {
  const yEWLeft = yEW * 0.3;
  const yNSLeft = yNS * 0.3;
  const Y = Math.min(0.92, yEW + yNS + yEWLeft + yNSLeft);   // 过饱和保护

  let cycle = Math.round((1.5 * lostTime + 5) / (1 - Y));
  cycle = Math.max(MIN_CYCLE, Math.min(MAX_CYCLE, cycle));   // clamp [60,150]

  const effective = cycle - lostTime;
  const alloc = (y: number, min: number): number =>
    Math.max(min, Math.round((effective * y) / Y));

  return {
    cycle,
    greens: [
      alloc(yEW, MIN_GREEN_THROUGH),      // 相位1 东西直行
      alloc(yEWLeft, MIN_GREEN_LEFT),     // 相位2 东西左转
      alloc(yNS, MIN_GREEN_THROUGH),      // 相位3 南北直行
      alloc(yNSLeft, MIN_GREEN_LEFT)      // 相位4 南北左转
    ],
    lostTime
  };
}
```

### 7.2 Webster 延误

```ts
// src/algo/delay.ts
export function websterDelay(cycle: number, greenRatio: number,
                             saturation: number, volumePerHour: number): number {
  const x = Math.min(0.95, saturation);            // 防止分母趋零
  const q = Math.max(0.05, volumePerHour / 3600);  // 辆/s
  const uniform = (cycle * Math.pow(1 - greenRatio, 2)) / (2 * (1 - greenRatio * x));
  const random  = Math.pow(x, 2) / (2 * q * (1 - x));
  return uniform + random;
}
```

### 7.3 流量仿真

```ts
// src/algo/simulator.ts
/** 确定性伪随机：与端侧 pseudo() 同算法，保证同一路口同方向结果稳定 */
export function pseudo(id: string, dir: string): number {
  const s = `${id}_${dir}`;
  let h = 7;
  for (let i = 0; i < s.length; i++) h = (h * 31 + s.charCodeAt(i)) % 9973;
  return h / 9973;
}

/** 高斯双峰：早 8 点、晚 18 点 */
export function peakFactor(hour: number): number {
  return 0.35 + Math.exp(-Math.pow(hour - 8, 2) / 4) + Math.exp(-Math.pow(hour - 18, 2) / 4);
}

export function simulateVolume(id: string, dir: string, hour: number): number {
  const base = 480 + pseudo(id, dir) * 420;        // 480 ~ 900 辆/h
  return Math.round(base * peakFactor(hour));
}
```

### 7.4 派生指标（与端侧 `TrafficUtil` / `getFlows()` 一致）

```
capacity(展示用) = 1650 × lanes × 0.48        // 绿信比固定，已知近似
saturation       = volume / capacity
queueLength      = round(saturation² × 14)
delay            = round(saturation × 45 + 6)
拥堵指数 index   = min(10, avg(全部进口道饱和度) × 10)
平均车速         = round(45 × (1 - avg / 1.6))
```

> **实测覆盖规则（`HybridDataSource`）**：命中实测的进口道用反推值替换 `saturation` 与 `queueLength`
> （`volume` 由饱和度 × 通行能力反算），并标 `source=BAIDU`；未命中保持上式仿真值并标 `SIM`。
> 畅通区段（`congestion_sections` 为空）只把饱和度约束到 `[0.2, 0.55]`，保留不同路口与时段差异。
> 片区均速优先用实测车速按路段长度加权。

> ⚠️ **评价模块待修正**：端侧 `getEvaluation()` 中通行量（`before=0.93V, after=V`）与停车次数（`before=1.6x, after=1.2x`）
> 为**构造值**，优化前基线（`C=120, λ=0.42`）亦为硬编码。迁移到后端时**必须改为逐周期排队推演**，
> 否则只是把演示性数字搬到服务端。详见 [项目设计文档 §10.7](./项目设计文档.md)。

## 8. OSM 真实路网导出（P3）

### 8.1 为什么用 OSM

免费、可离线、**无需 Key**，能拿到 WGS84 真实坐标与信号灯点位，论文"路网建模"章节可直接写"基于 OpenStreetMap 开源路网数据"。
地图厂商 API（花瓣/高德/百度）均不开放原始路网数据下载。

### 8.2 导出步骤

1. 打开 <https://overpass-turbo.eu/>，把地图定位到西安城墙内。
2. 执行以下 Overpass QL（bbox 为城墙范围）：

```
[out:json][timeout:60];
(
  node["highway"="traffic_signals"](34.2478,108.9286,34.2768,108.9774);
  way["highway"~"^(primary|secondary|tertiary)$"](34.2478,108.9286,34.2768,108.9774);
);
out body geom;
```

3. 导出 GeoJSON，筛选落在城墙范围内的信号灯节点与主干道。
4. 与现有 `INT_01~INT_20` 按名称/位置做人工匹配，生成 `data/network.ts`（保留原 id 不变，只替换坐标与路段几何）。
5. `intersection.source` 字段标记 `OSM`（匹配到）或 `MANUAL`（人工补录）。

### 8.3 已知风险

| 风险 | 对策 |
| --- | --- |
| OSM 国内信号灯点位**覆盖不完整**，20 个可能查不全 | 匹配到几个算几个，其余保留 `MANUAL` 并在论文中如实说明覆盖率 |
| 坐标与现手工值存在偏差 | 只替换明确匹配成功的路口，避免整体跳变 |
| 若改接高德/百度，坐标为 GCJ-02 | 需先转 WGS84（`src/util/geo.ts`），否则与 OSM/端侧体系不一致 |

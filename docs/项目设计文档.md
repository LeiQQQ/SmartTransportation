## 1. 项目定位

### 1.1 一句话定位

> 面向西安城墙内片区，构建一套 **"感知 → 优化 → 评价 → 服务"** 的交通信号配时闭环原型：以 Webster 模型按实时流量重算路口周期与绿信比，鸿蒙端将优化过程与结果可视化，并把算法结论翻译为用户可理解的信息（如"该方向还需等待 26 秒"）。

### 1.2 属于智慧交通的哪个子系统

| ITS 子系统 | 本项目覆盖 | 状态 |
| --- | --- | --- |
| ATMS（先进交通管理系统） | 信号配时优化、路段拥堵评估（核心） | ✅ 端侧已实现 |
| ATIS（先进出行者信息系统） | 路段态势发布、事件提示、路口等待时间 | ✅ 端侧已实现 |
| APTS（公共交通） | 不做 | — |
| AVCS / ETC | 不做 | — |

### 1.3 三个创新点（V2.1 改为可验证表述）

| # | 创新点 | 可验证的落点 | 状态 |
| --- | --- | --- | --- |
| 1 | **流量自适应的配时优化闭环** | 按进口道实时流量重算周期与绿信比，而非固定配时；周期、绿信比、延误可在 `SignalPlanPage` 逐项查看 | ✅ 算法链路已实现；⚠️ 优化前基线为构造值（§10.7） |
| 2 | **算法结果的用户化表达** | 把"周期 96s / 绿信比 34:15:20:12"翻译成"预计等待 26 秒 · 约 2 个周期通过"，见 `IntersectionDetailPage` | ✅ 已实现 |
| 3 | **零依赖可降级的路网可视化** | Canvas 自绘拓扑路网承载拥堵着色、手势交互与路口跳转，不依赖任何第三方地图 SDK 与网络 | ✅ 已实现；❌ 花瓣地图增强模式未做 |

> 说明：V2.0 中"双渲染引擎"因 Map Kit 需真机与签名证书、且本项目的叠加要素（相位、排队、倒计时）在真实底图上反而更拥挤，故**降级为可选增强**，不作为创新点主张。

## 5. 系统架构

### 5.1 当前实现架构（✅ 可运行）

```
┌─────────────────────────────────────────────┐
│  HarmonyOS 手机端（entry）                    │
│  ┌───────────────────────────────────────┐  │
│  │ 表现层 pages/ · components/            │  │

│  ├───────────────────────────────────────┤  │
│  │ 数据层 repository/                     │  │
│  │  ITrafficRepository ← MockRepository   │  │
│  │                     ← RemoteRepository │  │ ❌ 未实现
│  ├───────────────────────────────────────┤  │
│  │ 仿真与算法 mock/XianWallMock            │  │
│  │  流量仿真 · Webster 配时 · 延误 · 评价   │  │
│  ├───────────────────────────────────────┤  │
│  │ 工具层 common/utils                    │  │
│  │  TrafficUtil · FavoriteUtil            │  │
│  │  PreferencesUtil · ToastUtil · LogUtil │  │
│  └───────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
```

> 说明：**算法当前在端侧 `XianWallMock` 中实现**，为"纯端侧仿真"方案。接后端时只需新增 `RemoteTrafficRepository` 实现同一接口，页面零改动——这是当前分层设计保留的核心价值。

### 5.2 目标架构（❌ 未实现，接后端后的形态）

```
表现层 → Repository（三态工厂）
            ├─ RemoteTrafficRepository → HttpUtil → Node 后端（/api/v1）
            └─ MockTrafficRepository   → 本地仿真（远程失败时自动回落）
后端（Node 20 + TypeScript + Fastify）：
  routes → service → source（仿真 / OSM 路网 / 地图 API 预留）→ store（JSON → SQLite）
  算法引擎：Webster 配时 · Webster 延误 · 流量仿真（从端侧 ArkTS 平移）
  定时任务：5min 流量 / 15min 配时
```

✅ 已落地（2026-10-30）：`HttpUtil`、`ApiResponse`、`RemoteDtos`、`RemoteTrafficRepository`、三态 `RepositoryFactory`；Node 后端 11 个接口全部跑通。
未落地部分：`viewmodel/`、`renderer/`、后端落库（SQLite）与定时任务。

**数据源定位**（详见后端方案 §2）：配时输入**只能来自仿真**——地图开放平台（花瓣 / 高德 / 百度）均不提供进口道分方向流量与信号配时参数；地图 API 在本项目中用于**路网（OSM 导出）与底图**，不参与配时计算。

## 7. 功能模块设计

### M1 首页·态势总览 ✅

- 拥堵指数：`index = 各进口道饱和度算术平均 × 10`，上限 10，五级色阶，环形仪表绘制。
- 路网态势：20 个路口以彩色圆点 + 名称网格呈现，点击直达详情。
- 拥堵 TOP3：按饱和度降序，显示饱和度数值与等级色。
- 刷新：`Refresh` 下拉 + 右上角"刷新"按钮。

## 10. 核心算法

> 本章前半部分（10.1~10.6）为算法原理与实现口径，后半部分（10.7~10.8）如实说明**实现与经典模型的差异及局限**，答辩口径以本章为准。

### 10.1 参数取值与标定依据

| 参数 | 取值 | 依据 | 说明 |
| --- | --- | --- | --- |
| 饱和流率 `s` | 1650 辆/h/车道 | 城市主干道进口道单车道饱和流率常用取值区间 1600~1800 辆/h，取偏保守值 | 工程常用值，**未做现场标定** |
| 车道数 `n` | 1~3 | 按路口等级手工赋值（钟楼、大差市、西华门、五路口 3 车道；大皮院 1 车道） | 示意值 |
| 黄灯 `A` | 3 s | 城市道路信号灯常规黄灯时长 | 常见取值 |
| 全红 `AR` | 1 s | 小型交叉口清空时间 | 常见取值 |
| 总损失 `L` | 16 s | `L = 4 相位 × (黄灯 3s + 全红 1s) = 16s` | 🔶 **未单独计入启动损失**（约 2s/相位），故取值偏小 |
| 周期上下限 | 60~150 s | 单点定时信号周期不宜过短（< 60s 损失时间占比过高）或过长（> 150s 延误与排队陡增） | 区间约束通过 `clamp` 实现 |
| 最小绿灯 | 直行 10 s、左转 8 s | 满足行人过街与左转车清空的最低绿灯 | 🔶 与文档 V2.0"统一 10s"不同，左转实为 8s |
| 饱和度分级阈值 | 0.4 / 0.6 / 0.75 / 0.9 | 对应畅通 / 基本畅通 / 轻度 / 中度 / 严重五级 | 常用分级 |
| 平均车速换算 | `v = 45 × (1 - x̄/1.6)` | 自由流车速取 45 km/h，饱和度达到 1.6 时车速归零 | 示意换算，非标定模型 |

### 10.2 饱和度与分级

**Webster 流量比（配时用）**

```
y_i = q_i / s_i        q_i：第 i 关键相位流量（辆/h）；s_i：该相位饱和流率（辆/h）
x_i = y_i × C / g_i    饱和度（v/c），C：周期，g_i：有效绿灯
```

**展示用饱和度（列表/路网着色）**

```
capacity   = s × n × λ          λ：绿信比，当前固定取 0.48
saturation = volume / capacity
```

| 饱和度 v/c | 等级 | 颜色 |
| --- | --- | --- |
| < 0.4 | 畅通 | `#00C48C` |
| 0.4 ~ 0.6 | 基本畅通 | `#7ED321` |
| 0.6 ~ 0.75 | 轻度拥堵 | `#FFB020` |
| 0.75 ~ 0.9 | 中度拥堵 | `#FF7A45` |
| ≥ 0.9 | 严重拥堵 | `#FF3B30` |

> 🔶 两处口径不同：配时用的是 Webster 定义的流量比 `y = q/s`（不依赖绿信比）；展示用的饱和度引入了固定绿信比 `λ = 0.48`。原因是饱和度与绿信比互为因果，一次性求解存在循环依赖，当前取典型值解耦。**这是已知近似**，改进方向见 10.8。

### 10.3 Webster 最优周期

**目标函数**：使一个周期内全部进口道的总延误最小。

对第 `i` 个相位，Webster 均匀延误为：

```
d_i = C(1 - λ_i)² / [2(1 - λ_i x_i)]
```

总延误 `D = Σ q_i · d_i`（辆·秒），对周期 `C` 求极小。由于 `λ_i = g_i/C`、`Σg_i = C - L`，`D(C)` 无解析闭式解。Webster 通过数值寻优得到工程近似式：

```
C₀ = (1.5L + 5) / (1 - Y)
Y  = Σ y_i               （各关键相位流量比之和）
L  = Σ(每相位黄灯 + 全红 + 启动损失)
```

该式是**经验近似最优**，在 `0.4 ≤ Y ≤ 0.9` 区间与数值最优解偏差很小，是交通工程界通用的单点配时公式。

**有效绿灯分配**（按流量比等比例分摊有效绿灯时间）：

```
g_i = (C₀ - L) × (y_i / Y)
```

**约束处理**：

```
C₀ ← clamp(C₀, 60, 150)
g_i ← max(g_i, 最小绿灯)       直行 10s，左转 8s
```

> 注：当 `Y` 接近 1 时 `C₀` 趋于无穷，故实现中设 `Y ≤ 0.92` 的上限做**过饱和保护**；此时路口已超出定时控制能力，需靠渠化或区域协调解决，不在本项目范围内。

### 10.4 本项目的相位结构与流量比构造

四相位方案（两直行 + 两左转）：

| 相位 | 名称 | 流量比 | 最小绿灯 |
| --- | --- | --- | --- |
| 1 | 东西直行 | `y_EW = max(q_E, q_W) / (s · n)` | 10 s |
| 2 | 东西左转 | `y_EWL = 0.3 × y_EW` | 8 s |
| 3 | 南北直行 | `y_NS = max(q_S, q_N) / (s · n)` | 10 s |
| 4 | 南北左转 | `y_NSL = 0.3 × y_NS` | 8 s |

- 关键相位流量取**相位内两个进口道的较大值**（符合关键相位定义：一个相位内的通行能力由最拥挤的进口道决定）。
- 🔶 左转流量比按直行的 30% 折算，原因是仿真数据只生成进口道总流量、未拆分转向，属于**数据粒度不足导致的简化**。

### 10.5 Webster 延误模型

```
d = C(1-λ)² / [2(1-λx)]  +  x² / [2q(1-x)]
    └─── 均匀延误 ────┘     └── 随机附加延误 ──┘
λ = g/C（绿信比）  x = 饱和度  q = 流量（辆/s）
```

- 第一项：车辆均匀到达、红灯期间排队、绿灯后定率释放产生的延误。
- 第二项：车辆随机到达造成的过饱和附加延误（`x → 1` 时急剧增大）。
- 数值稳定处理：`x ≤ 0.95`、`q ≥ 0.05`，避免分母趋零。

### 10.6 流量仿真

**时段曲线**（高斯双峰，早 8 点 / 晚 18 点）：

```
f(h) = 0.35 + exp(-(h-8)²/4) + exp(-(h-18)²/4)
```

**基础流量**：

```
base(id, dir) = 480 + pseudo(id, dir) × 420        → 480 ~ 900 辆/h
volume        = round(base × f(h))
```

`pseudo` 为**确定性哈希伪随机**（字符串逐字符 `h×31+c mod 9973` 归一化到 [0,1)），作用是让不同路口、不同方向有不同的基准流量，同时保证**同一路口同一方向的结果稳定可复现**（避免每次刷新数字乱跳）。

**派生指标**：

```
饱和度     x     = volume / (s × n × 0.48)
排队长度   queue = round(x² × 14)          // 经验拟合，饱和时约 14 辆
平均延误   delay = round(x × 45 + 6)       // 线性拟合，x=0 时约 6s（基础损失）
```

**片区拥堵指数**：

```
index    = min(10, avg(全部进口道饱和度) × 10)
avgSpeed = round(45 × (1 - avg/1.6))
```

> 🔶 指数为**等权算术平均**，V2.0 文档写的"加权平均"与实际不符，V2.1 更正。

### 10.7 实现与经典模型的差异（如实说明）

| # | 环节 | 经典做法 | 本项目实现 | 性质 |
| --- | --- | --- | --- | --- |
| 1 | 相位流量比 | 逐相位独立采集转向流量 | 直行取关键进口道，左转按 30% 折算 | 数据粒度简化 |
| 2 | 总损失 `L` | 含启动损失（约 2s/相位） | `L = 16s`（仅黄灯+全红） | 参数偏小 |
| 3 | 饱和度 | `x = y·C/g`，与配时迭代收敛 | 展示用固定 `λ = 0.48` | 已知近似 |
| 4 | 排队 / 延误（展示） | 逐周期排队推演 / Webster 模型 | 经验拟合式 `x²×14`、`45x+6` | 拟合，量级与 Webster 相当 |
| 5 | 评价 · 优化前基线 | 同一仿真器跑固定配时 | 硬编码 `C=120`、`λ=0.42` | **构造基线** |
| 6 | 评价 · 通行量 | 仿真统计 | `before = 0.93V`，`after = V`（恒 +7.5%） | **构造值** |
| 7 | 评价 · 停车次数 | 仿真统计 | `before = 1.6x`，`after = 1.2x`（恒 -25%） | **构造值** |
| 8 | 时段切换 | 三套流量场景分别计算 | `scenario` 不参与计算，流量由系统时间决定 | 功能未闭环 |
| 9 | 随机性 | 泊松/负二项随机到达 | 确定性伪随机，无随机扰动 | 可复现但无波动 |

> **答辩口径**：周期、绿信比、Webster 延误三项由模型真实计算；**通行量、停车次数、优化前基线为演示性构造值**，只能表述为"估算/示例"，不能称为仿真统计结果。

### 10.8 局限性与改进方向

| 局限 | 影响 | 改进方向 | 优先级 |
| --- | --- | --- | --- |
| 评价基线为构造值 | 优化效果无法被独立验证 | 改为逐周期排队推演：以 5s 步长跑 30 分钟，按 `queue(t+1)=max(0, queue+到达-释放)` 累计延误、停车、通过数 | P1 |
| 饱和度与配时不自洽 | 展示饱和度与实际绿信比脱节 | 迭代求解：给定初始绿信比 → 算配时 → 回代饱和度 → 收敛（3~5 次即收敛） | P1 |
| 单点优化，无协调 | 相邻路口各自为政，干线不绿波 | 加入相位差计算（数解法 / MAXBAND），本项目方格网非常适合 | P3 |
| 无随机到达 | 指标恒定，无波动、无法体现过饱和随机性 | 引入泊松抽样 | P2 |
| 数据为仿真 | 无法证明参数适用性 | 实地计数 15 分钟标定 1~2 个路口的饱和流率与到达率 | P2 |
| `scenario` 未生效 | 时段切换按钮形同虚设 | 让 `scenario` 决定仿真小时数（早高峰 8.0 / 平峰 13.0 / 晚高峰 18.0） | P0 |

## 12. 接口设计（❌ 服务端未实现，仅为协议约定）

契约已定稿（V3.0），服务端未实现。前缀 `/api/v1`，**字段一律驼峰、时间用毫秒时间戳**，与端侧模型同名。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/health` | 健康检查 / 数据源探测（端侧三态降级依赖） |
| GET | `/area/intersections` | 路口列表（含进口道） |
| GET | `/area/segments` | 路段列表 |
| GET | `/traffic/index` | 片区拥堵指数 |
| GET | `/traffic/flow` | 全部路口实时流量（可带 `codes`） |
| GET | `/traffic/flow/{id}` | 单路口实时流量 |
| GET | `/signal/plan/{id}` | 当前配时方案 |
| POST | `/signal/optimize/{id}` | 触发优化，返回新方案 + 评价 |
| GET | `/signal/evaluation/{id}` | 优化前后对比（`scenario` 可选） |
| GET | `/events` | 事件列表（`type`、分页） |
| POST | `/events` | 事件上报 |

统一响应：`{ "code": 0, "message": "success", "data": {}, "timestamp": 0 }`

> 端侧 8 个仓库方法与此一一对应，接入时只需实现 `RemoteTrafficRepository`。
> 端侧需同步改造：`HttpUtil`、`ApiResponse`、`RemoteTrafficRepository`，`RepositoryFactory` 改为
> **`MOCK / AUTO / REMOTE` 三态**（`AUTO` 先探 `/health`，失败回落 Mock 并提示），保障答辩演示。
> 完整契约、请求响应字段与后端目录结构见 [后端技术方案 §6](./后端技术方案.md)。
